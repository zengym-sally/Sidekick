### F5 · P2：argv 观察遇到 EPERM 时，没有同时满足两条规范的否决原因编码

**位置**：`docs/engineering/web-api-contract-v2.md:78`、`:133`（类型定义同时见 `:69`、`:70`）。

**不变量**：同一个合法失败观察应有一致、可实施且可作为独立断言来源的 `attemptExitEvidence` 形状。

**证据**：第 78 行规定 argv 未执行/执行失败/命中时，`veto.reason` 只能为 `known_survivor` 或 `insufficient_evidence`；第 133 行却将“观察/清扫请求被操作系统拒绝”分类为 `eperm`。对一次被 OS 以 EPERM 拒绝的 argv 扫描，合法扫描形状是 `{performed:false,hits:0}`：编码为 `eperm` 违反第 78 行，编码为 `insufficient_evidence` 又不符合第 133 行的专门分类。已交的扫描失败样例仅覆盖泛化失败，组 EPERM 样例仅覆盖组观察，两者均未触及交叉情况。

**影响**：生产判定器与按另一条规范编写的契约测试会拒绝彼此的合法否决输出；这不是误释放的实测证据，但阻止把该稿冻结为唯一实施判据。

**建议**：明确通用扫描失败与 EPERM 的优先级/适用范围，例如扫描因 EPERM 失败时仍否决并使用 `eperm`，同步修正第 78 行的原因集合与第 133 行的通用失败表述，补一个独立扫描 EPERM 样例及机械断言。无论采用何种一致编码，扫描失败仍必须 `unresolved`、占槽且 resolve 拒绝；无需新增 owner 决策。

**复核方式**：`build/mayne35-api2-rereview/review_contract.py` 生成 `argv-eperm-logical-witness.json`，分别对照两条原因约束。它是合成逻辑见证，未执行真实 OS 扫描、未运行 E 生产代码。
