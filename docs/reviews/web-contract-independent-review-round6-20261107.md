## A 面：API/数据正确性 — APPROVE_WITH_CHANGES

### A1 · P2：暂存失败且副作用未知时，待核对失败的读取形状未定义

- 位置：`docs/engineering/web-api-contract.md:62`、`:114`、`:166`、`:171`。
- 不变量：暂存结局保留成功/失败判别，且用户能在处置前读取、核对该结局；接口不能只说明“可见”而没有明确的数据映射。
- 静态反例：暂存的是 failed 结局，退出回收后仍有未知副作用。§3.4 让任务保持 needs_review 并将暂存结局转为可见；结果端点已在白名单，但 §4.3 仅定义 kind/payload/acceptedByAttempt/completedAt 的结果形状，未说明 failed 暂存信封如何映射。任务 failure 又仍描述为终态失败信封，没有明确这一非终态的可见规则或读取入口选择。
- 影响：后端和客户端仍须各自决定从任务 failure 读、从结果 payload 读，还是等待处置完成后读，不能得到同一份“先核对错误、后处置”的公共预期。这是接口完整性缺口，不是已执行的端点失败。
- 现有样例 `tests/fixtures/web-contract/task-failed-result-reclaimed.json:28` 仅覆盖已经进入 failed 的终态；`task-result-read-needs-review-200.json` 覆盖的是成功 payload，因此本轮样例检查全绿没有否定这一缺口。
- 最小修正：选择并明确待核对失败的读取入口及形状。可以显式允许该 needs_review 状态经任务资源 failure 读取，或为结果响应定义有成功/失败判别的映射；不要求额外建设新接口。补同一任务“暂存失败＋退出已确认＋副作用未知→读回失败信封→人工处置”的 JSON，标清原失败判别和版本，不更改已有安全守卫。
