## 两缺口闭合裁定

**缺口 1（分段与 ACK 失效判据）——闭合（§11.1）。** 绑定键升级为 `(taskId, syncEpoch, task.version, attemptId, recovery.itemVersion)`（服务端提供 `recovery.itemId` 时并绑）——**协调层点名的陷阱被正面处理**：明文「不能仅以 taskId/epoch/itemVersion 绑定，因为新 attempt 的条目版本可能再次为 1」。失效规则完整：绑定任一成员改变/epoch 改变/卸载 → 废旧会话（停止旧分段请求、清旧部分/完整结果与完整标记、旧 ACK、旧会话专属错误/pending）；在途响应可结束但续体写状态前三重核对（生命周期/generation/当前绑定），作废响应不得写新行；发出 resolve 前再核当前绑定、旧勾选不得转用。确定性反例三条钉住陷阱本身：同 taskId 同 epoch **itemVersion 同为 1 但 attempt/task.version 已变**；同 attempt 但 itemVersion 已变；失效后旧末段才返回 done=true——三面均须证明旧结果不安装、不标完整、旧 ACK 不沿用、不发出携带旧核对状态的处置请求。

**缺口 2（并发视图版本单调安装）——闭合（§11.2）。** GET/PUT 共用同一权威视图的安装归属/接受水位，「各自不同 key 的最新 generation 不足」明文采纳（正是本审 r2 登记的洞）；同 epoch 内 `响应 version < 已显示 version` 禁止安装；**等版本迟到响应也不得覆盖较新请求已安装状态，须有共享请求代次判据**（对「应有明确判据」的直接回答）；PUT 成功响应被归属守卫丢弃时须统一围栏重读收敛、不得只清 pending 即视作完成；**新 epoch 重建水位基线**（避免单调守卫错误拒绝新 epoch 的合法低版本——本审 r2 未言明的次生陷阱已预防）；输入草稿与权威视图分离、409 重读保留草稿不自动重发（与 r2 一致）。反例五条（旧 PUT v1 晚于 GET v2/不同 key 交错/等版本迟到/换 epoch 合法低版本/409 保草稿）观察实际显示值而非守卫函数被调用，并要求删除共享归属或版本守卫的变异命中断言。
