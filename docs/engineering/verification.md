# 验证、门禁与证据约定（权威）

> 本文规定“改完怎么证明没坏”和“证据怎么留”。结构与放置规则见 [工程架构](architecture.md)；每轮必读的导航在仓库根 `AGENTS.md`。
> 门禁名称以 `package.json` 的脚本为准；本文只规定每道门的职责、顺序与证据要求，不复述脚本实现。

## Web/后端阶段的证据边界

交付顺序仍为 W0–W5 完整浏览器业务后 D1 薄壳，详见[分期验收](../product/04-分期交付与验收.md)。`npm run check` 已纳入 Web 手工事项、文本整理、任务控制、候选操作幂等、API2 客户端和退出证据生产/消费套件。浏览器真实 HTTP、受控模型/进程、真实服务、Linux 代理和 macOS 原生各自留证，不能相互代签。API1 历史夹具不再作为现行 API2 组合的正控；正控必须含现行规范字段，版本拒绝等负控保留。

## 1. 门禁矩阵

| 门禁 | 覆盖 | 何时跑 | 说明 |
|---|---|---|---|
| `npm run check` | 全量：**结构与文档守卫**（在首位）→ Runtime 打包 → 类型检查 → 各切片域测试 → Rust `fmt`／`clippy` → P2 运行时护栏 → 生命周期探针 → 既有 probe → 各 runtime／集成测试 → 两包构建与包内排除 | 切片收口、合并前、独立验证 | 单机串行，任一条失败即整体失败；不接受“部分命令通过”代替 |
| `npm run check:structure` | 生产前端跨层依赖、分层边界、顶层目录白名单、测试／脚本／Rust 目录收敛、打包入口存在性、`git ls-files` 入库卫生、旧路径残留、守卫负例自测 | 移动／新增文件、改顶层结构、改 `package.json` 路径后 | 先 `--self-test` 再查仓库；规则权威在 [工程架构](architecture.md) |
| `npm run check:docs` | `README.md`、`AGENTS.md`、`DESIGN.md`、`design/README.md`、`docs/**/*.md` 的本地相对链接存在性 | 改任何文档后 | 跳过代码围栏、行内代码、外部链接与锚点；`docs/reviews/**` 的历史记录不校验，但其 `README.md` 校验 |
| `npm run typecheck` | `vue-tsc --noEmit` | 改前端 TS／Vue 后 | 类型错误不进入构建 |
| `npm run check:rust` | `cargo fmt --check` + `cargo clippy -D warnings` | 改 Rust 后 | 与 `npm run check` 内的调用一致 |
| 聚焦脚本（`npm run test:*`、`npm run probe:*`） | 单切片业务规则、schema、配置、失败反例 | 开发中逐步回归 | 脚本名是稳定接口，不因目录调整改名 |
| `npm run check:s33-p2` | MCP P2 的域／存储／宿主／隔离护栏、类型与双特性 Clippy、先专用后普通构建与包排除 | 只改 P2 相关面时 | 有界聚合，**不能**代替完整 `npm run check` |
| 显式真实环境命令 | `npm run test:s2-live`／`test:s31-live`／`test:s32-live`、原生验收包 `build:*-verify`、`probe:app` | 需要真实模型、原生或安装包时 | 不进自动门禁；需要 owner 指定配置与显式授权，见第 3 节 |
| `npm run test:web-text-intake` / `test:web-task-controls` | 来源/候选/签收、队列/恢复/权威条目、SSE 与生产工作台；任务控制读回与并发围栏 | Web 切片与整合后 | 使用真实存储、受控服务；不代表真实外部服务 |
| `npm run test:web-candidate-operations` | HTTP 重放/重启幂等与生产 CandidateCard 的 operationId 生命周期 | 候选操作或集成后 | 默认验证当前树，历史 D 基座可显式指定并核身份；无需另一个任务工作区 |
| `npm run test:web-api-v2` / `test:web-exit-evidence` | 现行接口/快照、证据披露、登记域生产与消费、持久化失败关闭 | API2 / 退出 / 集成后 | 不声称证明任意逃逸进程树消亡；真实 OS 观察边界单列 |
| `node --check <script>` | 新增／修改的 `.mjs` 脚本语法 | 触碰守卫或打包脚本后 | 轻量前置，不替代执行 |

已知非阻断输出：esbuild 对随包 Runtime 的体积提示、Vite chunk 体积提示、ad-hoc 签名与未公证提示。它们属于既有基线；**新增**警告必须在验证记录里逐项归因，不能默认忽略。

## 2. 测试分层

- **单元（`tests/unit/`）**：纯域规则、客户端模型、JSON／配置解析。不依赖构建产物、不启动进程、不访问网络与真实用户目录。
- **集成（`tests/integration/`）**：需要先打包 Runtime、构建 Rust example 或拉起子进程的测试（生命周期、发现、原生 FD、各切片 runtime、`s32-live`）。允许启动并强杀自建测试进程，但不得访问真实模型、真实凭据或用户工作根。
- **探针（`tests/probes/`）**：probe 契约、bundle 冒烟、卡片与运行时探针，以及切片输入（如 `tests/probes/s33/`）。按需接入 npm 脚本。
- **合成输入（`tests/fixtures/`）**：输入、配置与服务；不含断言，不作为“已实现”证据。
- **Rust**：业务库测试随 `store/` 各模块的 `*_tests.rs` 平铺；用 `cargo test --lib <filter>` 运行，过滤器依赖模块名，模块名因此不能改；需要原生征集的用 `src-tauri/examples/` 与特性门控。

写测试的纪律：先写能失败的反例，再实现；断言来自独立预期，不照抄实现输出；“替身通过”只能证明替身覆盖的那一段，不能外推成真实服务、系统钥匙串或原生 GUI 通过。新测试用领域命名并放进对应分层，切片名只用于历史文件。

## 3. 证据与新鲜度

- 证据必须来自**实际执行**：命令原文、退出码、通过／失败计数、日志路径、必要的源与产物哈希。没有执行的项写“未验证”，不得写成通过。
- **不重用旧结果**：代码、依赖、配置或迁移变化后，受影响门禁必须重跑；历史记录里的通过只证明当时版本。运行前记录基点 commit 与工作区状态。
- **替代关系**：浏览器合成 IPC 不能代替 Tauri／真实 IPC；Rust 替身不能代替系统钥匙串；本地合成模型服务不能代替真实模型；单元测试不能代替原生动线。每层证据只覆盖自己那一层，并在记录里写明边界。
- **历史版本**：记录中的路径与哈希属于当时版本；复核历史内容用 `git show <commit>:<path>`，不按当前工作区重算哈希。目录迁移后不改写历史记录，新记录使用新路径。
- **冻结**：收口时生成代码哈希清单（源文件与关键产物），供之后比对“记录之后是否又改过代码”。
- **未验证项**：必须在验证记录与实施状态里逐条列出并保持开放，例如原生 GUI 动线、真实凭据、真实用户根迁移、干净检出构建、真机安装。它们不因相邻项通过而关闭。

## 4. `docs/reviews/` 留存策略

- 每条评审／验证记录是 `docs/reviews/<slice>-<YYYYMMDD>.md`；证据目录同名，少数早期目录命名不同（见 [记录索引](../reviews/README.md)）。
- **原始证据默认不入库**：中间日志、临时产物、截图批量放 `build/<slice>/`（已在 `.gitignore`），可重建、可覆盖。
- **入库只收精选主证据**：能让第三方复核结论的最小集合——证据 JSON／摘要、关键命令日志、关键截图、哈希清单。大体积原始日志留在 `build/`。
- 记录必须自足：范围与风险级、基点 commit、实际命令与退出码、计数、未验证项、结论（pass／needs_revision／reject 或 GO 类结论的限定）。
- **不删除历史记录与证据**；纠正错误用追加说明或新记录，不把旧结论改写成“当时通过”。索引与留存规则见 [评审记录索引](../reviews/README.md)。
- 新记录默认写入“精选主证据”；只在确有复核价值时把证据文件加入仓库，并在记录里说明取舍。

## 5. 独立验证与评审

- **实现、验证、评审分离**：实现者不给自己出验证结论，也不签署自己的评审。验证方独立执行完整门禁并做静态复核；评审方只读，按维度出结论。
- **验证的最小内容**：完整 `npm run check`（含结构与文档守卫）、旧路径残留静态检索、`git status` 与 `git diff --stat -M` 核对、纯移动性抽查、警告分类对照基线、结论 pass／fail。验证方不自行修复，发现问题交回实现方。
- **评审的判据**：架构面看边界与结构是否与文档、守卫一致，迁移是否纯移动，扩展点与已知债是否如实；实现面看等价性（模块名、公开路径、测试过滤、特性构建、schema／依赖／配置是否变化）与报告是否与验证证据一致。
- **结论只能是 pass／needs_revision／reject**；needs_revision 与 reject 必须带文件／行号与必需修正。评审通过不等于测试通过，二者证据不能互相替代。
- **风险分级**：涉及跨进程契约、凭据与安全边界、数据迁移、依赖或 vendor 的改动按 R3 处理——双面评审 + owner 授权；纯文档与文档链接修复可按低风险处理，但仍需 `check:docs`。
- **授权边界**：提交、推送、发布、真实凭据访问、真实用户根迁移都需要 owner 明确授权；验证与评审不构成这些授权。

## 6. 开放项与 CI 缺口

- **没有 CI**：全量门禁只在本机由人触发，单机串行；这既是成本也是风险（忘记跑、环境漂移无法自动发现）。新增 CI 需要平台与凭据决策，属于开放项，本轮不实现。
- **干净检出构建未纳入常规门禁**：Pi 源码准备需要网络与固定上游版本；干净克隆的完整构建仍是手工验证项。
- **原生与真实环境无法自动化**：原生 GUI 动线、屏幕捕获、系统钥匙串、真实模型与飞书调用都需要显式授权与人工观察，只能按切片留证。
- **文档守卫的范围有限**：只验证本地相对链接存在，不验证语义正确；文案与事实一致性仍靠评审。
- **何时补 CI**：当出现第二台常跑机器、或需要对外分发时再评估；把本机 `npm run check` 作为唯一准出运行是当前接受的残余风险。
